# Governing principles

Code comments across this repo cite these by number, as "Principle 5" or "Principle 9". This file
is what they cite.

They are constraints on what the system is allowed to do, not style preferences. Most of them are
enforced by something stronger than review: a database constraint, an unreachable call graph, or a
test. Where that is true it is stated, because a principle nothing enforces is a wish.

A note on provenance, in the spirit of Principle 5: these were reconstructed from the roughly 120
places the code cites them, after the working file that originally held them was removed from the
repository. Each one below is supported by code that references it, and the enforcing mechanism
named in each is real and checkable. Principle 8 is not cited anywhere in the codebase, so it is
left out rather than invented to close the numbering.

---

## Principle 1: the agent produces evidence, a human decides

The detector's `risk_score` and the verifier's `outcome` never freeze, block, capture or refund
anything by themselves. Only a recorded row in `merchant_decisions` may trigger an action.

Enforced structurally, not by convention. `razorpay-capture.ts`'s capture and refund functions are
unreachable from the detector, the webhook handler and every scheduled job. Their single call site
is the holds router, inside a handler that has already loaded a merchant-supplied decision.

The strongest form of this is in `packages/db/src/schema/holds.ts`: the agent's power is limited to
**not acting**. It declines to capture an authorised payment. Razorpay auto-refunds anything left
uncaptured after three days, so the failure mode expires in the customer's favour, and the agent
never moves money in either direction.

## Principle 2: the whole chain is auditable

Detection, decision and execution each write a structured `audit_log` record. Detection is part of
the audit chain, not just the merchant's later decision.

The detector's own explanation is stored verbatim, so the dashboard renders the agent's actual
reasoning rather than the dashboard's paraphrase of it. `GET /api/clusters/:id` returns members,
evidence, verifications, decisions and the audit log in one call, so the full history of a cluster
is one request rather than a reconstruction.

## Principle 3: guarantees are database constraints, not application checks

Anything that must be true is a constraint. Application-level checks exist to produce a friendly
error message, never to be the guarantee.

Idempotency is unique indexes plus `ON CONFLICT DO NOTHING`: `accounts.customer_ref`,
`transactions.razorpay_event_id`, and `account_links_pair_signal_uidx`. A Razorpay retry, two
deliveries racing, or a re-uploaded CSV export cannot duplicate a row, and that holds even for a
client that bypasses the API and writes to Postgres directly. `tests/test_idempotency.py` proves it
by doing exactly that.

## Principle 4: rules first, and log which path answered

Transcript parsing is rule-based. An LLM assist is reserved for genuinely ambiguous transcripts, and
every verification record carries `handled_by` naming the path that produced it.

The LLM-assisted path is **not wired**. No LLM credential exists in this repo, and recording a
result as `"llm"`-handled without actually calling one would be a Principle 5 violation. When the
rules cannot safely pick a side, the outcome is `unclear`. Forcing a guess there would manufacture
exactly the confidence Principle 5 forbids.

## Principle 5: never invent a number

Every metric in the README, the docs, the landing page and `/evidence` is read from a JSON file that
a script wrote. If a measurement does not exist, the code and the docs say it does not exist.

Consequences visible in the codebase:

- `razorpay-client.ts` and `razorpay-capture.ts` are labelled NOT YET EXERCISED AGAINST THE LIVE API,
  because every environment this project has run in blocks egress to `api.razorpay.com`.
- There is no rupee figure for the cost of a false positive, because no chargeback rate, verification
  friction or churn rate has been measured. The 1:4 cost ratio in `model_comparison.json` is labelled
  a policy dial, not a measurement.
- `chargeback_exposure.py` computes exposure, money currently at risk, and refuses to present it as a
  record of chargebacks that happened, because the generator does not model chargebacks at all.

This is the principle the project's credibility rests on. It is also why every number in the docs
names the file it came from.

## Principle 6: this is a synthetic-data sandbox, and says so

Every account, transaction, address, phone number and transcript is generated by
`generate_synthetic_data.py` or `generate_synthetic_responses.py`, both deterministic under a fixed
seed. No real Razorpay merchant, customer or transaction data is used anywhere.

Executing a decision therefore means recording what it would trigger, honestly. The audit record for
an executed decision states that no real Razorpay API was called, rather than silently implying a
live payment processor was contacted.

## Principle 7: claim only the languages that are actually demonstrated

The architecture supports Sarvam's full language catalogue. Only `en-IN`, `hi-IN` and `mr-IN` are
ever claimed to work live, and the keyword banks, opening scripts and closing lines exist for those
three only.

The scripts have not had a fluent-speaker review. That is disclosed rather than glossed.

## Principle 9: never an unlabelled connection

Every edge in the graph is one specific shared signal between two accounts, carrying its
`signal_type` and its `confidence`. There is no generic "these are related" edge, in the database,
in the API or in the graph the dashboard draws.

This extends to explanations. `cluster_scorer._explain` derives its plain-language reasons from the
same values that produced the score, never written independently of it, so the evidence and the
account of the evidence cannot drift apart.

## Principle 10: a dismissal requires a reason

Dismissing a flagged cluster, or rejecting a held payment, requires a stated reason. It is enforced
by `merchant_decisions_dismiss_reason_check` at the database level, not by a required field in the
UI.

The reason is measurement infrastructure. A dismissal without a stated cause is how a
false-positive rate stops being computable, and the false-positive count is the honest cost signal
this project has in place of a rupee figure it cannot measure.

## Where these are enforced

| Principle | Enforced by                                                                       |
| --------- | --------------------------------------------------------------------------------- |
| 1         | Call-graph isolation of capture/refund; `merchant_decisions` gating in `holds.ts` |
| 2         | `audit_log` writes at detection, decision and execution                           |
| 3         | Unique indexes + `ON CONFLICT DO NOTHING`; `tests/test_idempotency.py`            |
| 4         | `handled_by` on every verification record; `unclear` as a real outcome            |
| 5         | Every number read from `data/*.json`; explicit not-exercised labels in the code   |
| 6         | Seeded generators; audit records that name the sandbox                            |
| 7         | Keyword banks and scripts exist for three languages only                          |
| 9         | `account_links` check constraint on `signal_type`; `_explain` derives from score  |
| 10        | `merchant_decisions_dismiss_reason_check`; 400 from the decision and hold routes  |
