# AI Risk Manager - Fraud Ring Detection Platform

Built for Razorpay Buildathon Track 2. **All data in this repository is synthetic** - accounts,
transactions, phone numbers, addresses, and the voice-verification transcripts are generated by
`services/detector-service/generate_synthetic_data.py` and
`services/verifier-service/generate_synthetic_responses.py`, both deterministic (fixed seed 42),
committed to `data/`, with train/test splits that are never cross-contaminated. No real Razorpay
merchant, customer, or transaction data was used anywhere in this build.

> **Picking this up in a new session (human or AI)?** Read
> [`HANDOFF.md`](HANDOFF.md) first. It is the complete briefing: the hard rules, the algorithm,
> every measured number and the file it comes from, the known failures, and the environment traps
> that have already cost hours.

Rendering behavior, database query improvements and verification commands are documented in
[`docs/performance.md`](docs/performance.md).

## What this actually is

Razorpay's existing Thirdwatch product scores individual transactions for fraud. This project
detects a different, harder problem it doesn't cover: **coordinated fraud rings** - clusters of
accounts that share signals (delivery address, payment fingerprint, phone pattern, promo code,
coordinated timing) in ways that suggest one actor operating multiple identities, as opposed to
one bad transaction. The product is a three-part pipeline behind one merchant-facing dashboard:

1. **Detector** (`services/detector-service`, Python/FastAPI) - builds a graph of accounts
   connected by shared signals, runs community detection (Louvain) to find clusters, and scores
   each cluster's risk and estimated chargeback exposure.
2. **Verifier** (`services/verifier-service`, Python/FastAPI) - for a borderline cluster, places
   an automated multilingual call (English, Hindi, Marathi) asking the account holder whether
   they're aware of the linked account, and parses the response with a rule-based, keyword-driven
   parser (not an LLM - see "Why rules, not an LLM" below).
3. **Dashboard** (`web/next` + `api/hono`) - the actual product surface. Every flagged cluster
   shows its network graph (every edge labeled with the exact signal and confidence - never an
   unlabeled connection), a plain-language evidence panel, the verification transcript if one
   exists, and four merchant actions: Freeze, Block, Escalate, Dismiss. **Nothing in this system
   ever acts autonomously** - the detector's risk score and the verifier's outcome only ever
   inform a human; only a merchant's explicit decision (recorded with a full audit trail) can
   freeze, block, or dismiss a cluster.

## Why community detection, not a Graph Neural Network

A GNN is the current state of the art for fraud-ring detection (see FraudNet's 2026 marketing,
which specifically names GNNs as necessary for this exact problem). It's also the honest,
deliberate trade-off this build did **not** make: a GNN needs more labeled training data and
engineering time than a 10-day solo build allows. Louvain community detection on the shared-signal
graph is the MVP choice, stated as a trade-off rather than hidden as a limitation, with a GNN as
the explicit next step (see `Architecture.md` §3).

## Why a rule-based parser, not an LLM, for voice verification

The verifier's response parser (`response_parser.py`) is deliberately rule-based: keyword banks in
three languages (English, Hindi, Marathi - Devanagari and romanized spellings both), matched with
one shared, longest-match-first, non-overlapping span so a phrase like "aware of" can't spuriously
match inside "not aware of" (a real bug this project found and fixed - see "What broke" below).
When no keyword confidently resolves the transcript, or confirm/deny signals genuinely conflict,
the parser returns `unclear` rather than forcing a guess. This is intentional per this project's
own engineering rules: a rule-based-first parser with an honest `unclear` outcome is safer than an
LLM call that always produces _a_ confident-sounding answer, on a decision that can lead to an
account being frozen.

One subtlety worth calling out explicitly, because it's an easy place to introduce a silent bug:
in the _original_ single-transaction fraud design, a customer confirming a transaction meant it
was legitimate. In _this_ ring-verification context, the meaning inverts - confirming awareness of
the linked account (`confirmed_linked`) leans **legitimate** (a family member, a shared
household), while denying any knowledge (`denied_linked`) **strengthens** the fraud-ring
hypothesis. `Design.md` §3 calls this out by name.

## Honest metrics

All numbers below are read from files this repository's own scripts produce
(`data/detector_metrics.json`, `data/verifier_metrics.json`, `data/batch_run_report.json`) -
not hand-typed, and re-derivable by anyone who clones this repo and runs the two `evaluate*.py`
scripts themselves.

**Detector, held-out test split** (`services/detector-service/evaluate.py`, never trained/tuned
against this data):

| Metric                                | Before (flat weighted sum)         | Now (corroboration-gated) |
| ------------------------------------- | ---------------------------------- | ------------------------- |
| Recall on true rings                  | 100% (5/5)                         | **100% (5/5)**            |
| Precision on flagged clusters         | 41.7%                              | **100% (5/5)**            |
| Legitimate households wrongly flagged | 7/7 surfaced, 2 at high confidence | **0/7**                   |

Score separation on the held-out split: rings **0.59–0.79**, households **0.28–0.30**.

The precision gain came from finding a real modelling bug, not from tuning weights: the old flat
sum double-counted a single fact, because `density` and `avg_confidence` are re-observations of the
same signal rather than independent corroboration of it. Three flatmates sharing one address make a
fully-dense, high-confidence triangle - one fact, counted three times. The fix scores how many
_independent_ kinds of signal tie a group together, and caps any group whose every connection has
an ordinary household explanation. Full write-up: [`docs/algorithm.md`](docs/algorithm.md).

The flagging threshold (0.45) is selected on the **training** split by
`services/detector-service/select_threshold.py`, by a rule fixed in advance, and applied unchanged
to the held-out split. A hand-guessed 0.60 would have cost 23% recall - which is why it is chosen
by script, not by eye. The choice is auditable in `data/threshold_selection.json`.

**Adversarial stress test** (`services/detector-service/stress_test.py`, `data/stress_test_report.json`) - **8/10**

The held-out households are easy: they share exactly one signal. Ten harder cases were built on
purpose, and two of them fail:

- **False positive** - flatmates sharing an address, a card, order timing _and_ one funnelled promo
  code (0.70, flagged). On the five signals available this is genuinely indistinguishable from
  promo abuse. It is the case the voice verifier exists for: escalate to asking, don't act.
- **False negative** - a ring using _only_ coordinated timing (0.39, held back). Correct by design:
  "ordering at the same time" is what families do. The deliberate side of the trade.

**What these numbers don't prove.** The held-out split validates the _implementation_ - the
algorithm does what it claims on data it never saw. It cannot validate the _assumption_, because
`generate_synthetic_data.py` encodes the same belief the scorer does (households share an address,
not a sequential SIM block or a funnelled promo). Real validation needs real merchant data with
real chargeback outcomes.

**Detector, full dataset** (`services/detector-service/run_batch.py`, train+test combined,
396 unique accounts, run unattended, no exception):

| Metric                                                   | Before | Now       |
| -------------------------------------------------------- | ------ | --------- |
| Recall on true rings                                     | 17/18  | **17/18** |
| Legitimate households wrongly flagged at high confidence | 9/22   | **0/22**  |

The remaining 1/18 miss is a _clustering_ limit, not a scoring one, and is unchanged by the Phase 10
redesign - see the "what broke" note below. The false-positive count going 9 → 0 at four times the
data volume is the corroboration gate holding up outside the held-out split.

Both false-positive numbers are legitimate households flagged with no chargeback/rupee figure
invented for them - this project's synthetic data doesn't model chargeback rates or verification
friction, so a manufactured currency number would be exactly the kind of fabricated confidence
this project's own engineering rules forbid. The honest signal is the count and the risk-score
distribution, reported as-is.

**Verifier, held-out synthetic response set** (`services/verifier-service/evaluate_verifier.py`,
39 entries, 3 languages × 4 outcomes):

| Metric   | Value        |
| -------- | ------------ |
| Accuracy | 100% (39/39) |

Caveat that belongs next to that number, not hidden below it: 100% on a self-authored synthetic
test set is not the same claim as accuracy on independent or adversarial transcripts. The
still-outstanding step that would actually test that is a live Sarvam AI call in Hindi and
Marathi, checked by a fluent speaker (Phase 0's exit criteria) - not yet done, and disclosed here
rather than implied.

### The trained model, and the dataset that made it possible

The first attempt at this comparison produced a useless answer: **every** method scored a perfect
1.000 average precision on the held-out split, including an isolation forest fitted with no labels
at all. A score an unlabelled model also reaches is measuring the exam, not the student. The cause
was the dataset - `generate_synthetic_data.py` gives rings all five signals and households exactly
one, so the two classes are separable on a single feature and there is nothing to learn.

`generate_hard_dataset.py` fixes that. It grades both populations until they overlap:

- **Rings**, sloppy to careful: all five signals / no shared address / no shared card either /
  promo + timing only / a SIM block alone / coordinated timing alone.
- **Legitimate groups**, easy to genuinely ambiguous: a shared address / a family card / a family
  that also orders at the same hour / flatmates who also pass one coupon around / an office
  delivery address / a reseller using one card across many addresses.

2,613 accounts and 11,815 transactions in train, 1,185 / 5,341 held out. Rings also carry
second-order structure the five signals do not capture - burst signup, order amounts clustered just
above a promo floor, promo concentration, uniform cadence - which is what a model can learn and the
hand-built rule does not look at. That is an assumption about fraud, disclosed as one.

**Held-out results on the graded split** (`data/model_comparison.json`):

| Method                                 | Precision | Recall   | Costly errors |
| -------------------------------------- | --------- | -------- | ------------- |
| **Hybrid (heuristic + random forest)** | **90.9%** | **100%** | **4**         |
| Random forest                          | 87.0%     | 100%     | 6             |
| Gradient boosting                      | 85.1%     | 100%     | 7             |
| Hist gradient boosting                 | 85.1%     | 100%     | 7             |
| Logistic regression                    | 76.9%     | 100%     | 12            |
| Extra trees                            | 76.9%     | 100%     | 12            |
| Corroboration heuristic alone          | 66.0%     | 82.5%    | 45            |
| Isolation forest (**no labels**)       | 0.645 AP  | -        | -             |

"Costly errors" is `false_positives x 1 + false_negatives x 4`, and the operating threshold is
chosen to minimise it on the TRAINING split - not by F1, which silently asserts that holding a real
customer's payment and letting a fraudulent one settle hurt equally. The 1:4 ratio is a policy dial
stated in the report, not a measurement; there is still no calibrated rupee figure and inventing
one would be fabricated confidence.

On the ten hand-authored adversarial cases the trained model scores **9/10 against the heuristic's
8/10** - no regression off-distribution, and one case better: it catches `ring_maximally_evasive`,
which the rule deliberately holds back. That margin is a single case and should be read as one, not
as a general ranking. A model trained on the OLD easy split scores 6/10 on the same cases, newly
flagging two ordinary households, which is the clearest evidence that the harder dataset rather
than the bigger ensemble is what produced the gain.

**The model runs in the live agent.** `train_model.py --dataset hard --export` writes
`data/ring_model.joblib` plus a model card; `model_scorer.py` loads it inside detector-service and
`POST /detect-rings` scores with it, keeping the heuristic's plain-language explanation alongside
and reporting both verdicts so disagreement stays visible. If scikit-learn or the model file is
absent the service degrades to the heuristic and `GET /model` says so out loud. Reasoning in full:
`docs/algorithm.md`.

## What broke (and what that says about the system)

Two real, disclosed failures, found by actually running evaluation scripts against held-out data
rather than by inspection:

**The verifier's parser had two real overlap bugs**, caught by a first `evaluate_verifier.py` run
that came back at 84.6% (33/39), not 100%. First: "nahi" inside the longer phrase "mahit nahi" was
being counted as a second, separate deny-signal hit, occasionally outweighing a genuine hedge and
flipping an intended `unclear` case to `denied_linked`. Second, and more interesting: confirm,
deny, and hedge keywords were each checked with their _own_ independent overlap-suppression pass,
so "aware of" (a confirm keyword) still matched as a substring _inside_ "not aware of" (itself
matched by the deny keyword "not aware") - overlap suppression only worked within one category,
never across them. Both are fixed by scoring all three categories against one shared,
longest-keyword-first span map. This is exactly the kind of bug a rule-based system can produce
quietly and a held-out evaluation run catches loudly - which is the argument for running one.

**The detector's recall degrades at full scale, for a real, explainable reason.** Recall on the
5-ring held-out test split is 100%; at full scale (all 18 true rings), it's 17/18. The one miss,
`ring_010` (4 accounts), gets absorbed by Louvain into a larger, 10-account predicted cluster once
the graph is denser - the two clusters overlap enough (IoU 0.400) to almost, but not quite, clear
this project's 0.5 match threshold. This is not a code bug; it's the actual trade-off documented
above: Louvain community detection is sensitive to graph density in exactly the way a GNN would
not be, at the cost this build deliberately accepted to ship in 10 days.

## Setup

```bash
bun install         # workspace dependencies
cp .env.example .env
# set POSTGRES_URL  -  `bunx pglaunch -k` for a scratch Postgres, or point at docker-compose's
bun run db:migrate  # applies packages/db/drizzle/*.sql, including 0005_account_idempotency.sql
bun run dev          # runs web (Next.js) + api (Hono) via turbo
```

The two Python services need their own environment (they are not part of the Bun workspace):

```bash
pip install -r services/detector-service/requirements.txt
pip install -r services/verifier-service/requirements.txt
```

Or run the whole stack, including a local Postgres, with `docker compose up` (see
`docker-compose.yml`) - not smoke-tested this session (no Docker daemon reachable in either
environment that touched this repo; see `HANDOFF.md` §10 for the environment constraints).

## Running the tests

```bash
# TypeScript (workspace-wide)
bun run check-types

# Python  -  detector, verifier, and API-idempotency test suites (stdlib unittest, no
# pytest/plugin dependency)
python3 -m unittest discover -s tests -v
```

`tests/test_clustering.py` and `tests/test_cluster_scorer.py` need `networkx` installed.
`tests/test_idempotency.py` and `tests/test_audit_logging.py` need a real Postgres reachable via
the `POSTGRES_URL` environment variable - both SKIP cleanly (not fail) if either dependency isn't
present, rather than reporting a false pass.

## Regenerating the metrics this README quotes

```bash
python3 services/detector-service/evaluate.py            # -> data/detector_metrics.json
python3 services/detector-service/run_batch.py           # -> data/batch_run_report.json
python3 services/verifier-service/evaluate_verifier.py   # -> data/verifier_metrics.json
python3 services/detector-service/generate_hard_dataset.py  # -> data/hard_train.json, hard_test.json
python3 services/detector-service/train_model.py --export   # -> data/model_comparison.json + ring_model.joblib
python3 services/detector-service/make_figures.py        # -> docs/images/ (docs + slides)
```

`train_model.py` and `make_figures.py` need `services/detector-service/requirements-analysis.txt`
(scikit-learn, numpy, matplotlib). Neither is installed in the detector-service container and
neither runs on the live `/detect-rings` path - they are offline analysis, run by hand, whose
output the dashboard reads. `make_figures.py` renders the static figures used by `docs/` and the
submission write-up; the dashboard's own charts are drawn live from the same JSON by
`web/next/src/components/fraud/animated-charts.tsx`. Both read the run reports, so neither can
disagree with the run that produced them.

`GET /api/metrics` (`api/hono/src/routers/metrics.ts`) reads the first and third of those files
directly and combines them with live funnel counts (clusters flagged / verified / decided) queried
from Postgres - offline, held-out evaluation numbers and live operational counts, kept explicitly
separate in the response so neither is mistaken for the other.
