# AI Risk Manager

Razorpay Buildathon, Track 2. A merchant console that finds **coordinated fraud rings**: groups of accounts that look like separate customers but share signals no honest household produces. Razorpay Thirdwatch scores one payment at a time. This product scores the **graph between accounts**.

All data in this repository is synthetic. Accounts, phones, addresses, and verifier transcripts are generated by `services/detector-service/generate_synthetic_data.py` and `services/verifier-service/generate_synthetic_responses.py` (fixed seed 42), committed under `data/`, with train and test never mixed. No real Razorpay merchant or customer data was used.

**The agent never captures, refunds, or cancels money.** Detection and voice only produce evidence. A named merchant decision is the only thing that can freeze a cluster, capture a hold, or refund a hold. If nobody decides, Razorpay's authorization window expires and the customer is refunded.

## Stack

| Layer               | Path                           | Role                                                                         |
| ------------------- | ------------------------------ | ---------------------------------------------------------------------------- |
| Dashboard           | `web/next`                     | Next.js 16 console: queue, holds, analysis, evidence, metrics, live voice    |
| HTTP API            | `api/hono`                     | Hono on Bun. Ingest, detect, holds, webhooks, OpenAPI at `/api/openapi.json` |
| Schema              | `packages/db`                  | Drizzle + Postgres. Idempotency and dismiss-reason checks live in SQL        |
| Detector (measured) | `services/detector-service`    | Python FastAPI: graph, Louvain, corroboration scorer, optional hybrid model  |
| Detector (fallback) | `api/hono/src/lib/detector.ts` | Same signals and Louvain in TypeScript when the Python sidecar is down       |
| Verifier            | `services/verifier-service`    | Rule-based transcript parser (en-IN, hi-IN, mr-IN). Not an LLM               |
| Voice               | `api/hono/src/lib/sarvam.ts`   | Sarvam Bulbul TTS + Saaras STT. Speaks and listens. Does not move money      |
| Payments            | Razorpay manual capture        | Agent holds by **not capturing**. Merchant release calls capture             |

```
Razorpay webhook / CSV ingest
        │
        ▼
   Postgres (accounts, transactions)
        │
        ▼
   POST /api/clusters/detect
        │
        ├─ Python detector-service  (published metrics)
        └─ TypeScript Louvain       (serverless fallback; response says which ran)
        │
        ▼
   Flagged clusters + labeled edges
        │
        ├─ Voice (optional)  ask, do not act
        └─ Merchant console  freeze / hold release / reject
        │
        ▼
   audit_log  one chain: evidence → verification → decision → execution
```

## Detector

1. **Graph** (`graph_builder.py`). Nodes are accounts. Edges are one labeled signal with a confidence: shared address, shared payment fingerprint, sequential phone pattern, coordinated timing, shared promo. Timing and promo require at least two co-occurrences.
2. **Clusters** (`clustering.py` and the TypeScript port). Louvain. Not a GNN. A GNN needs more labeled rings than this build has. That is a stated trade-off.
3. **Score** (`cluster_scorer.py`). Corroboration, not density. A family sharing an address and a card is capped below the flag line. Flagging needs a fraud-specific signal (funnelled promo, SIM block) or two distinct weak fraud-specific types.
4. **Threshold** (`select_threshold.py`). 0.45, chosen on **train only**. A hand-picked 0.60 would have cost 23% recall.
5. **Stop.** Persist flagged clusters and write the reasoning into `audit_log`. No money moves.

The TypeScript engine uses the same Louvain port. Node visit order is sorted rather than Python's shuffled seed, so the densest graph (`hard_train.json`) still differs on 9 / 209 communities. Every published number in `data/*.json` was produced by the **Python** path. A fallback run says so on the response.

Write-up: [`docs/algorithm.md`](docs/algorithm.md). System map: [`Architecture.md`](Architecture.md). Console contract: [`Design.md`](Design.md).

## Why a rule parser, not an LLM

`services/verifier-service/response_parser.py` matches keyword banks in English, Hindi, and Marathi (Devanagari and romanized) with one shared longest-match-first span. Confirming a **linked account** leans legitimate (family). Denying it strengthens the ring hypothesis. That is the inverse of a "did you make this payment" verifier. Unclear stays unclear. An LLM that always returns a confident label is the wrong tool on a freeze decision.

Live voice (`POST /api/voice`) **asks** cancel vs release. It does not execute capture or cancel. The dashboard still has to confirm.

## Honest metrics

Numbers below are from files this repo's scripts write. Re-run the scripts to regenerate them. They are not typed by hand.

**Detector, held-out easy split** (`data/detector_metrics.json`, 5 rings / 7 households, never used for training):

| Metric                        | Flat weighted sum      | Corroboration-gated |
| ----------------------------- | ---------------------- | ------------------- |
| Recall on true rings          | 100% (5/5)             | **100% (5/5)**      |
| Precision on flagged clusters | 41.7%                  | **100% (5/5)**      |
| Legitimate households flagged | 7/7, 2 high confidence | **0/7**             |

Rings 0.59–0.79, households 0.28–0.30. The precision jump is a modelling bug fix: `density` and `avg_confidence` were counting the same shared address three times.

**Adversarial suite** (`data/stress_test_report.json`): **8/10**. False positive: flatmates who also pass one coupon (indistinguishable on these five signals; voice exists for this). False negative: a ring that only coordinates timing (held back on purpose).

**Full easy dataset** (`data/batch_run_report.json`, 396 accounts): 17/18 true rings recovered at IoU 0.5. 0/22 households flagged at high confidence. The miss (`ring_010`) is Louvain absorbing a 4-account ring into a 10-account community (IoU 0.400 vs the 0.5 match rule). Clustering limit, not a scoring bug.

**Verifier** (`data/verifier_metrics.json`): 39/39 on a self-authored synthetic set. That is not independent-transcript accuracy. Fluent-speaker review of Hindi and Marathi scripts is still outstanding.

**Graded (hard) split, live hybrid model** (`data/ring_model_card.json`, `data/model_comparison.json`):

| Method                             | Precision | Recall   | Costly errors (FP×1 + FN×4) |
| ---------------------------------- | --------- | -------- | --------------------------- |
| Hybrid (heuristic + random forest) | **95.2%** | **100%** | **2**                       |
| Random forest                      | 95.2%     | 100%     | 2                           |
| Hist gradient boosting             | 92.9%     | 97.5%    | 7                           |
| Extra trees                        | 80.0%     | 100%     | 10                          |
| Gradient boosting                  | 80.0%     | 100%     | 10                          |
| Logistic regression                | 78.4%     | 100%     | 11                          |
| Corroboration heuristic alone      | 66.0%     | 82.5%    | 45                          |
| Isolation forest (no labels)       | 0.645 AP  | n/a      | n/a                         |

Threshold chosen on train by expected cost, not F1, taking the midpoint of the widest band of thresholds tied at the minimum so the operating point does not sit on the edge of a plateau. The 1:4 cost ratio is a policy dial in the report, not a rupee measurement. The model always runs **next to** the heuristic; disagreement stays visible. Missing sklearn or a model-card mismatch falls back to the heuristic and `GET` on the detector's `/model` says so.

These numbers validate the **implementation** on synthetic data whose generator encodes the same household-vs-ring assumption the scorer uses. They do not validate that assumption on real chargebacks.

## Setup

```bash
bun install
cp .env.example .env
# POSTGRES_URL, BETTER_AUTH_SECRET, and the rest: see .env.example
# Production URLs belong in the host env, never in git
bun run db:migrate
bun run dev
```

Python sidecars (not in the Bun workspace):

```bash
pip install -r services/detector-service/requirements.txt
pip install -r services/verifier-service/requirements.txt
```

Full stack including local Postgres: `docker compose up`. Compose points API and detector at the compose Postgres, not at whatever `POSTGRES_URL` is in `.env`.

Required for live voice: `SARVAM_API_KEY` on the API process. Required before storing Razorpay secrets: `RAZORPAY_CREDENTIAL_KEY`.

## Tests

```bash
bun run check-types
bun test tests
python3 -m unittest discover -s tests -v
```

Python tests that need `networkx` or `POSTGRES_URL` skip (they do not fake a pass) when the dependency is missing.
